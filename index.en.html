Where the methods come from, and what the plugin adds

Original methods, Pi’s workflow organization, and this plugin’s cross-host implementation.

Pinned sources and adoption scope →

  1. 01 · Engineering methods

    Matt Pocock skills

    Methods for requirements discussion, specifications, ticketing, implementation and review. Use them on their own or combine them freely.

  2. 02 · Workflow organization

    Pi Matt

    Organizes the methods into a Pi product: a unified entry, five routes, phase transitions, dependent references and structured questions.

  3. 03 · This plugin

    Cross-host implementation

    Uses Pi’s implemented behavior as the porting baseline, adapts it to each host’s capabilities, and adds local handling:

    • Separate packages and acceptance for Codex, Claude Code and Devin CLI
    • Shared task state: resume after interruptions, with traceable answer receipts
    • Unresolved requirements cannot simply be recorded as complete
    • Only a real answer counts as a decision; empty replies and timeouts never choose for you

The layers are not a copy chain: this plugin also adopts some new Matt capabilities directly and keeps local extensions such as the writing route. New upstream changes do not enter the plugin automatically.

BDD · MAKE “RIGHT” CONCRETE

From a request to verifiable behavior.

Teaching example: add tag filtering to a task list.
The following is not a record of tests that ran or passed.

01 / SHARED UNDERSTANDING

Agree on behavior first

Should multiple tags match any or all selections? What appears when nothing matches? Resolve these business choices first.

02 / CONCRETE SCENARIOS

Express expectations as examples

Given: the list has “Work” and “Study” tasks.
When: only the “Work” tag is selected.
Then: only tasks tagged “Work” appear.

03 / EXECUTABLE VERIFICATION

Make implementation answer the scenario

Verify results through the public feature boundary. First show that the test catches missing behavior, then implement it and check clearing and empty-result scenarios.

Check this chain at delivery

Key behavioral scenario → corresponding test or observation → result and evidence → remaining unverified scope

Specification, ticketing, implementation and review load BDD references. Loading them does not prove they were followed, and test counts do not establish business outcomes. Define acceptance scenarios independently →
