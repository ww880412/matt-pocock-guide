01 / RECOVERY

The context still says “in progress”,
but the task has moved on.

When an old session resumes, its marker still points to implementation, but the source instance has since completed. Following that stale context alone would reactivate finished work.

Old marker → Check source events → Keep terminal state

Recovery must trace the source facts

A marker must match the source session ledger and an event with the same state. Completed or cancelled states for the same instance remain terminal during recovery.

What this guarantees An old phase record cannot reactivate a finished instance. If history is untrusted or unavailable, recovery limits remain explicit.
See implementation locations

sdk/restore/index.mjs: recovery and source-event validation; core/restore/index.mjs: Matt state merging and terminal-state rules; sdk/kernel/store.mjs: events and locks.

02 / DECISIONS

A late answer to the last question
cannot answer the current one.

After question A is replaced, a reply to its old card may still arrive. Seeing “agree” does not let the model decide question B on that basis.

Answer to A → Check question / source → B stays unresolved

Verify interaction evidence before consuming an answer

The Codex bridge reads native records from a trusted session and checks question linkage, submission order, and validity. Its interface rejects model-supplied answers and arbitrary transcript paths.

What this guarantees An old answer cannot count as a valid answer to a new question. Without a unique link, the plugin does not guess the user's choice.
See implementation locations

native/proof.mjs: host records and question linkage. native/server.mjs: bind / collect, accepting reply references only. Both are in the Codex native adapter directory.

03 / DELIVERY

State was saved,
but the method content never arrived.

A call records state but is interrupted during output. The next trigger must redeliver content while recognizing the state change that already occurred.

Event recorded → Delivery unconfirmed → Reuse event, resend content

Separate task progression from content delivery

claim marks an event awaiting delivery; ack follows output. The same pending event can be redelivered, and recognized call retries reuse the original event.

What this guarantees Redelivery has an explicit event identity. A receipt proves only the corresponding output step: it does not prove the model followed the method or guarantee exactly-once external side effects.
See implementation locations

sdk/delivery/index.mjs: claim / ack / unclaim; core/delivery.mjs retains compatibility exports. runtime/server.mjs: invocation-source deduplication and output receipts.

03 / ARCHITECTURE TRADEOFFS

Where control ends and reuse begins

Judgment boundary

Give code the rules it can check

Code validates legal routes, pending questions, unresolved requirements, and matching resource versions. Whether a design is correct or requirements are sufficient remains a matter for model judgment and human acceptance.

Cost and boundary The plugin cannot guarantee professional quality. The substance of completion evidence still needs real validation.

Host boundary

Share the core, retain adapter differences

Use the host's existing model loop, tools, and sessions. Integrate hooks, MCP, and native questions per host; share task rules and keep every package self-contained.

Cost and boundary Protocols and interaction still need validation by host. New host versions may require adapter updates.

Abstraction boundary

General mechanisms in the SDK, domain rules in Matt

Task State SDK provides state and locks, persistent decisions and receipts, command recovery, content delivery, and host protocol adapters. Matt defines routes, menus, capabilities, and product policies. RAC uses a pinned snapshot and has passed component acceptance as a second consumer.

Cost and boundary Consumers supply their runtime and domain model. SDK versions and contracts are maintained independently; the SDK does not guarantee exactly-once external operations.

Codex native.22 added whole-spec implementation and retrospectives for 38 capabilities. The agent uses existing host tools to maintain the task graph, owners, and worktrees, merges serially against the latest integration branch, and reviews the same candidate. retro reads evidence and proposes changes. No background scheduler or SDK state format was added. See new capabilities and bounded validation; Claude and Devin host validation and distribution are recorded separately.
